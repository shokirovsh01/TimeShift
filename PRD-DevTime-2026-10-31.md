## 1. Обзор приложения и цели

### 1.1 Что это
DevTime — веб-платформа с Telegram-ботом: цифровой бартер знаний и тайм-банкинг для локальных сообществ разработчиков. Участники помогают друг другу с IT-задачами и расплачиваются **часами**, а не деньгами: **1 час помощи = 1 час помощи**.

### 1.2 Проблема
- Опытные участники тратят время на чужие баги без отдачи.
- Новички стесняются спрашивать и подолгу сидят в тупике.
- Ценные решения тонут в переписке группового чата.

### 1.3 Цели продукта
1. Превратить хаотичную взаимопомощь в структурированную экономику с понятным балансом.
2. Сделать вклад каждого участника видимым (репутация, граф навыков, верифицированное портфолио).
3. Запустить закрытый бета-тест внутри одной учебной группы.

### 1.4 Критерии успеха беты `[ПРЕДПОЛОЖЕНИЕ]`
| Метрика | Целевое значение |
|---|---|
| Зарегистрированные участники группы | ≥ 70% группы |
| Закрытые контракты за первые 4 недели | ≥ 20 |
| Доля задач, получивших отклик | ≥ 60% |
| Доля участников, закрывших ≥ 1 контракт | ≥ 40% |

### 1.5 Вне рамок MVP
Деньги и платежи, настоящий блокчейн, мобильное приложение, мульти-сообщества, видеозвонки внутри платформы, ИИ-подбор исполнителей.

## 3. Основные функции и acceptance criteria

Функции сгруппированы под спринты (см. раздел 8).

### F1. Аутентификация и профиль
**Описание:** вход через Telegram, профиль с навыками.

- Вход через Telegram Login Widget; сессии Django (cookie-сессия).
- При первом входе создаётся `User` + `Profile`, начисляется стартовый баланс (`[ПРЕДПОЛОЖЕНИЕ]`: 2 часа).
- Профиль: отображаемое имя, bio, список навыков (из справочника `Skill`), публичная страница.
- Привязка Telegram: `telegram_id` (уникальный) сохраняется при входе, бот использует его для уведомлений.

**Acceptance criteria**
- Пользователь входит через Telegram одним кликом и попадает на дашборд.
- Повторный вход не создаёт дубликат профиля.
- Пользователь может добавить/удалить навыки в профиле.
- Новый профиль имеет стартовый баланс, записанный как транзакция в журнале (см. F5), а не просто число.

**Technical Considerations**
- Проверка подписи данных Telegram Login Widget (HMAC-SHA256 с ключом на основе токена бота) и проверка свежести `auth_date`.
- Документация: Telegram Login Widget, Django authentication.

### F2. Биржа задач (Bounty Board)
**Описание:** каталог микро-задач с ценой в часах и фильтрацией по навыкам.

- Создание задачи: заголовок, описание, теги-навыки (1–5), цена в часах (шаг 0.25 ч, `[ПРЕДПОЛОЖЕНИЕ]` диапазон 0.25–4 ч), формат помощи (созвон / ревью кода / переписка).
- Каталог открытых задач: фильтр по навыкам, сортировка по новизне и цене, поиск по тексту.
- Карточка задачи: автор, цена, навыки, статус, список откликов.
- Автор может редактировать задачу, пока нет исполнителя, и отменять её.

**Acceptance criteria**
- Нельзя создать задачу, если доступный баланс (баланс минус зарезервированное) меньше цены.
- При создании задачи цена **резервируется** (escrow) на балансе автора.
- Каталог показывает только задачи со статусом `OPEN`; фильтр по нескольким навыкам работает как «любой из выбранных».
- Отмена задачи без исполнителя возвращает резерв автору.

### F3. Отклик и выбор исполнителя
- Любой участник, кроме автора, может откликнуться на `OPEN`-задачу с короткой запиской и предлагаемым слотом времени.
- Автор видит отклики и выбирает одного исполнителя (бронь времени).
- Выбор исполнителя переводит задачу в `IN_PROGRESS`; остальные отклики получают статус `REJECTED` и уведомление.

**Acceptance criteria**
- Один пользователь — один активный отклик на задачу.
- Автор не может откликнуться на свою задачу.
- После выбора исполнителя новые отклики невозможны.
- Исполнитель и автор получают уведомление в Telegram.

### F4. Коллаборация и закрытие контракта
- Платформа не проводит сам созвон: участники договариваются о ссылке/месте во внутренних контактах (Telegram-username партнёра показывается только участникам контракта) `[ПРЕДПОЛОЖЕНИЕ]`.
- Исполнитель отмечает «помощь оказана» → задача `AWAITING_CONFIRMATION`.
- Автор подтверждает завершение и оставляет отзыв (оценка 1–5 + текст) → создаётся `HelpContract`, часы переводятся исполнителю.
- Если автор не подтверждает за 72 часа, система автоматически подтверждает `[ПРЕДПОЛОЖЕНИЕ]`.
- Оспаривание: автор может открыть спор → статус `DISPUTED`, решение за куратором группы.

**Acceptance criteria**
- Перевод часов происходит атомарно: резерв автора списывается, баланс исполнителя увеличивается, обе записи попадают в журнал.
- Повторное подтверждение одной и той же задачи не приводит к двойному начислению.
- После закрытия контракта отзыв виден на публичном профиле исполнителя.

### F5. Тайм-банк (учёт часов)
- Баланс участника хранится в `Profile.time_balance`, но **источник истины — журнал транзакций** (`TimeTransaction`, только добавление записей).
- Типы транзакций: `INITIAL_GRANT`, `ESCROW_HOLD`, `ESCROW_RELEASE`, `TRANSFER`, `ADMIN_ADJUSTMENT`.
- История операций на странице профиля.
- Баланс не может уйти ниже 0 (`[ПРЕДПОЛОЖЕНИЕ]`: отрицательный кредит запрещён в MVP).

**Acceptance criteria**
- Сумма всех транзакций пользователя всегда равна его `time_balance` (проверяется ежедневной management-командой сверки).
- Одновременные запросы не могут создать отрицательный баланс (блокировка строки в БД).
- Любая операция с часами оставляет запись с автором, суммой, связанной задачей и временем.

**Псевдокод перевода (алгоритм, не код реализации)**
```
функция завершить_контракт(task):
    начать транзакцию БД
        заблокировать профили автора и исполнителя
        проверить: task.status == AWAITING_CONFIRMATION
        проверить: контракт по task ещё не создан
        списать резерв автора (запись ESCROW_RELEASE)
        начислить reward_hours исполнителю (запись TRANSFER)
        создать HelpContract(helper, helped_user, hours, отзыв)
        task.status = COMPLETED
        пересчитать репутацию исполнителя
    зафиксировать транзакцию
    отправить уведомления
```

### F6. Репутация и граф навыков (геймификация)
- Репутация исполнителя растёт после каждого закрытого контракта: зависит от часов и оценки в отзыве `[ПРЕДПОЛОЖЕНИЕ]`: `+часы × оценка`.
- Граф навыков: визуализация связей «кто кого и в чём выручал» (узлы — участники, рёбра — закрытые контракты, подписи — навыки).
- Верифицированное портфолио: публичная страница профиля с навыками, числом закрытых контрактов, отзывами и суммарными часами помощи.

**Acceptance criteria**
- Страница портфолио доступна по постоянной ссылке и показывает только подтверждённые контракты.
- Граф строится по данным `HelpContract` и отображает минимум 100 узлов без заметных тормозов.
- Репутация пересчитывается только при завершении контракта.

### F7. Telegram-бот-ассистент
- **Новые квесты:** подписка на навыки/теги, уведомление о новых подходящих задачах.
- **Быстрый отклик:** кнопка «Откликнуться» в сообщении бота.
- **Контроль баланса:** команда `/balance`, уведомления о начислении и списании часов.
- Уведомления о событиях контракта: новый отклик, выбор исполнителя, запрос подтверждения, закрытие.

**Acceptance criteria**
- Привязка аккаунта: пользователь, вошедший через виджет, получает сообщения от бота после команды `/start`.
- Отклик из бота создаёт тот же `Response`, что и отклик с сайта (одна бизнес-логика).
- Пользователь может отключить уведомления по тегам.
- Недоставленное сообщение (бот заблокирован) не ломает основной процесс, ошибка логируется.

### F8. Администрирование и модерация
- Django Admin для куратора: просмотр пользователей, задач, споров, ручная корректировка баланса (с обязательным комментарием, пишется в журнал).
- Возможность скрыть задачу или заблокировать пользователя.

## 4. Рекомендации по техническому стеку

| Слой | Выбор | Почему | Альтернатива |
|---|---|---|---|
| Backend | Python 3 + Django | Админка и ORM «из коробки», быстрый MVP | FastAPI: гибче, но админку и auth писать самому |
| БД | PostgreSQL | Транзакции, блокировки строк — критично для баланса часов | SQLite: проще, но слабее при конкурентной записи |
| Frontend | Django-шаблоны + Tailwind CSS (+ HTMX для интерактива) | Один деплой, нет отдельного SPA, достаточно для дашборда | React SPA: богаче, но вдвое больше работы |
| Бот | Aiogram | Современная асинхронная библиотека для Telegram Bot API | python-telegram-bot |
| Фоновые задачи | Celery + Redis или Django-Q `[ПРЕДПОЛОЖЕНИЕ]` | Авто-подтверждение через 72 ч, рассылки | cron + management-команды (проще для беты) |
| Граф навыков | D3.js или Cytoscape.js | Готовые библиотеки визуализации графов | vis-network |

**Моя главная рекомендация по боту.** Aiogram асинхронный, Django по умолчанию синхронный. Самый простой путь для беты: запустить бота **отдельным процессом**, который общается с бизнес-логикой через общий слой сервисов Django (или внутренний REST API). Так не придётся смешивать два event loop. Бот работает через long polling на старте, на проде можно перейти на webhook.

**Ключевое архитектурное решение:** вся бизнес-логика денег-часов живёт в одном сервисном слое (`services/`), а не в сигналах. В презентации упомянуты «сигналы пересчёта баланса» — для простоты и надёжности советую **явные сервисные функции** вместо Django signals: их легче тестировать и они не запускаются неожиданно.

Документация: Django (docs.djangoproject.com), Aiogram (docs.aiogram.dev), Tailwind (tailwindcss.com/docs), Telegram Bot API (core.telegram.org/bots/api).

## 6. Принципы UI/UX

Из презентации: современный тёмно-синий акцент с индиго и оранжевым, чистые светлые карточки со скруглениями, моноширинный шрифт для технических акцентов.

**Основные экраны**
1. Вход (Telegram Login).
2. Дашборд: баланс часов, активные контракты, рекомендованные задачи.
3. Bounty Board: каталог с фильтрами по навыкам.
4. Карточка задачи: описание, отклики, действия по статусу.
5. Создание задачи.
6. Мой профиль и публичное портфолио.
7. Граф навыков и менторства.
8. История операций тайм-банка.

**Принципы**
- Баланс часов всегда виден в шапке.
- Один главный призыв к действию на экран («Откликнуться», «Подтвердить»).
- Статусы задач различаются цветом и текстом (не только цветом).
- Адаптивная вёрстка (mobile-first: большинство зайдёт с телефона по ссылке из Telegram).
- Пустые состояния с подсказкой, что делать дальше (особенно для новичков).
- Дружелюбные формулировки: никаких «долг», «должник» — вместо этого «ты ещё можешь помочь».

Wireframes в презентации отсутствуют — рекомендую набросать 4 ключевых экрана (дашборд, каталог, карточка задачи, профиль) перед спринтом 2.

## 7. Соображения по безопасности

| Риск | Мера |
|---|---|
| Подделка входа через Telegram | Проверка HMAC-подписи и `auth_date` на сервере |
| Двойное начисление / гонки при переводе часов | Транзакции БД + блокировка строк (`select_for_update`), идемпотентность подтверждения |
| Накрутка репутации (взаимные «сделки» между друзьями) | Лимит контрактов между одной парой за период, видимость аномалий куратору |
| Фарм часов фиктивными задачами | Ограничение цены задачи и числа открытых задач на пользователя |
| Утечка контактов | Telegram-username партнёра виден только участникам контракта |
| CSRF/XSS | Стандартная защита Django, экранирование пользовательского текста, CSP |
| Токен бота и секреты | В переменных окружения, не в репозитории |
| Закрытость беты | Доступ по инвайт-коду или проверке членства в Telegram-группе `[ПРЕДПОЛОЖЕНИЕ]` |
| Персональные данные | Хранить минимум: Telegram ID, имя; возможность удалить профиль |
| Спам-ботом | Ограничение частоты (rate limit) на отклики и создание задач |

## 8. Этапы разработки (milestones)

| Спринт | Содержание | Результат |
|---|---|---|
| **0. Подготовка** | Репозиторий, Django-проект, PostgreSQL, Tailwind, конфиги окружений | Запускаемый «скелет» |

| **3. Тайм-банк и контракты** (F4, F5) | Журнал транзакций, резервирование, закрытие, отзывы, споры | Полный цикл сделки |
| **4. Telegram-бот** (F7) | Aiogram-бот, уведомления, быстрый отклик, `/balance` | Мгновенные оповещения |
| **5. Репутация и граф** (F6) | Расчёт репутации, портфолио, граф навыков | Геймификация |
| **6. Бета-запуск** | Тесты, сид-данные, деплой, онбординг группы, сбор обратной связи | Закрытый бета-тест |

Каждый спринт завершается демо на реальных данных и фиксацией найденных проблем.

## 9. Потенциальные проблемы и способы их решения

| Проблема | Решение |
|---|---|
| **Холодный старт:** на бирже нет задач и нет исполнителей | Стартовый баланс, сид-задачи от организатора, личный призыв первых 10 участников |
| **Дисбаланс:** все хотят получать, никто не помогает | Стартовый баланс небольшой, напоминания бота «Тебе доступны N задач по твоим навыкам» |
| **Низкое качество помощи** | Отзывы, оценка, возможность спора |
| **Часы «зависают»** у неактивных авторов | Авто-подтверждение через 72 ч, напоминания, лимит на открытые задачи |
| **Неравная ценность часа** (час новичка и час сеньора) | Принятая модель «1 час = 1 час»; ценность различает репутация, а не цена |
| **Конфликт async (Aiogram) и sync (Django)** | Отдельный процесс бота + общий сервисный слой |
| **Сложность ведения графа** на больших данных | Ограничение глубины/фильтры, кэш запроса графа |
| **Правовые нюансы** | В MVP часы не конвертируются в деньги и не продаются; зафиксировать это в правилах сообщества |

Терминология: «смарт-контракты» из презентации в MVP означают **записи `HelpContract` в БД**, а не блокчейн-контракты. Рекомендую так и назвать в коде, чтобы не вводить в заблуждение.

## 11. Нефункциональные требования

- **Производительность:** страницы каталога открываются < 1 с при 200 пользователях и 500 задачах.
- **Масштаб беты:** до 200 пользователей, до ~50 одновременных сессий.
- **Надёжность:** ежедневный бэкап БД; ежедневная сверка баланса с журналом.
- **Наблюдаемость:** логирование ошибок бота и операций с часами.
- **Тестирование:** обязательные автотесты на логику резервирования, перевода и граничные случаи баланса.
- **Локализация:** русский язык интерфейса, структура готова к добавлению других языков.
